## Context

平台后台没有注册。平台管理员必须能登录，但组织角色、打开平台后台的路由、Cookie 或 Header 都不能产生这个身份。

## Decision

用独立的平台任职表记录事实。受信部署操作者可通过 `platform admin create` 直接创建邮箱已验证的 `platform_admin`，密码通过标准输入传入。固定数据库函数在同一事务创建账号、原生密码凭据、任职与审计；不发送验证邮件或创建会话，邮箱重复时失败。

已有用户先通过正常认证注册和验证邮箱，再由 `platform assignment grant/revoke` 以精确 UUID、role 和非空 reason 管理任职。grant 仍检查用户存在且邮箱已验证；这两个命令不创建账号或修改验证状态，也不提供 HTTP 任职管理接口。

CLI 使用专用部署连接 `PLATFORM_ASSIGNMENT_DATABASE_URL`，不向在线 API 注入该凭据。API 统一使用 `DATABASE_URL`，每次平台请求重新检查权威 Session 与有效任职；撤销后旧 Session 的下一请求被拒绝。

## Alternatives

- 公开注册的首位用户自动成为平台管理员：注册和平台任职分别产生事实；否决。
- CLI 给已存在且已验证邮箱的用户授权：复用正常账号认证和邮箱验证，以精确 UUID 明确指定目标；采用。
- CLI 创建邮箱已验证的平台管理员：原决定否决；2026-10-16 根据用户确认采用，限专用部署身份创建新账号，不初始化会话或 MFA。
- 组织 owner 自动成为平台管理员：两个任职会互相推导；否决。

## Consequences

平台身份与组织角色独立。部署操作者可以直接创建管理员，或向已验证用户授予任职；平台 MFA 为账号自选项；未启用者可用密码直接登录，主动启用后保留原生两步验证流程。部署身份不能读取密码、修改已有账号或为既有用户追加密码凭据。真实 CLI/平台访问测试用于验证这些边界，不表示已经完成生产部署。
