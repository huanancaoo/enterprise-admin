## Context

The platform console has no registration. A platform admin must be able to log in. Organization roles, opening the platform route, cookies, or headers must not create that identity.

## Decision

Record platform identity in a dedicated assignment table. A trusted deployment operator can use `platform admin create` to create an email-verified `platform_admin`, passing the password through standard input. A fixed database function creates the user, native password credential, assignment, and audit in one transaction. It sends no verification mail and creates no session; an existing email fails the operation.

Existing users still register and verify their email through normal authentication. The `platform assignment grant/revoke` commands accept an exact user UUID, role, and non-empty reason. A grant requires an existing verified user; these commands do not create accounts or change verification state. No HTTP assignment management endpoint is exposed.

The CLI uses the dedicated deployment connection `PLATFORM_ASSIGNMENT_DATABASE_URL`; that credential is not injected into the online API. The API shares `DATABASE_URL` and checks the authoritative session and current assignment on every platform request. Revocation rejects the old session's next request.

## Alternatives

- First publicly registered user becomes platform admin: registration and platform assignment are separate facts. Rejected.
- CLI grants existing users with a verified email: reuse normal authentication and email verification, then select the target by exact UUID. Accepted.
- CLI creates an email-verified platform admin: originally rejected; accepted on 2026-10-16 following the user's decision, restricted to a dedicated deployment identity and new accounts, without initializing a session or MFA.
- Organization owner automatically becomes platform admin: the two assignments would derive from each other. Rejected.

## Consequences

Platform identity remains independent from organization roles. Operators can create an admin directly or grant an assignment to an existing verified user. MFA is optional: users without it can sign in with a password, while users who enable it retain the native two-factor login challenge. The deployment identity cannot read passwords, change existing accounts, or append credentials to existing users. Real CLI/platform-access tests validate these boundaries without establishing a production deployment.
