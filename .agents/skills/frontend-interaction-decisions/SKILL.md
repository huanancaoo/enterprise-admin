# 前端交互决策

先确定用户要完成的业务任务，再选择交互语义，最后映射当前项目的组件。组件库提供实现手段，不提供业务答案。

## 决策流程

### 1. 建立事实基线

从需求、产品文档、接口契约和现有代码中确认：

- 用户、业务目标，以及 Create、Edit、Show 等具体界面任务。
- 信息结构、操作风险、完成时长、来源上下文和稳定 URL 需求。
- 字段含义、候选集合、验证约束、录入频率和字段间关系。
- 数据集总量、增长趋势、单次返回量、同时渲染量和服务端查询能力。
- 当前项目已有的设计系统、组件及交互约定。

Create、Edit、Show 分别建模。不得因为属于同一业务对象就预设相同载体。

完成标准：每个会改变交互语义、数据契约或业务行为的已知事实都有权威来源；其余产品决策已经确认或进入决策前沿。

### 2. 询问未决产品问题

事实由 Agent 查证，产品取舍由用户决定。把前置条件已明确、彼此独立的阻塞问题放在同一轮；依赖未决答案的问题留到下一轮。每题说明影响并给出基于当前事实的推荐答案：

```md
❓ **Q1 - <决策标题>**：<需要用户决定的问题>

➡️ 我建议 **<答案>**。<与当前业务事实直接相关的理由>
```

明确需求不重复询问。未确认的数据规模或重排范围不得自行补全；未确认的 DataTable 能力或其他产品行为不得启用。

问题范围只覆盖会改变当前交付物的决定。相邻业务规则仅在缺少答案会阻塞当前载体、控件、布局或数据呈现决策时进入决策前沿；其余保持原范围，不扩展成新的产品设计任务。

完成标准：不存在会让两种合理实现产生不同产品行为的未决问题。

### 3. 选择语义

只读取当前任务需要的分支：

- 选择 Dialog、Sheet 或独立页，或审查 CRUD 载体时，读取 [references/interaction-carriers.md](references/interaction-carriers.md)。
- 选择字段控件、字段宽度、分组或响应式表单布局时，读取 [references/forms.md](references/forms.md)。
- 选择列表、Table、DataTable、数据能力、分页、虚拟化、排序或重排时，读取 [references/tabular-data.md](references/tabular-data.md)。

一个任务涉及多个分支时读取对应的多个文件。按照语义规则排除不合适的方案；不要通过字段数量、记录数量或加权评分直接选组件。

完成标准：每项选择都能追溯到用户任务和已确认事实，而不是组件库存或机械阈值。

### 4. 映射并交付

先在当前项目中寻找能够表达已选语义的组件及既有模式。复用合适的现有组件；无法表达时指出具体能力缺口，不改变业务决策来迁就组件库。

需要新增服务端查询能力时，将其写成当前方案的契约前提；除非用户要求后端实现，否则不修改后端。路由、字段、查询参数和接口名称只使用权威来源中已有的精确标识符；来源未定义时描述所需语义，不自行命名。

按用户请求交付：

- 设计：给出选择、关键理由、必要的数据契约和排除项。
- 实现：只实现已确认的能力，并验证完整交互链路。
- 审查：指出选择与业务事实不一致的位置、影响和正确方向；未要求修改时不改代码。

完成标准：载体、控件、布局、数据处理位置和实际组件彼此一致，且没有加入未确认能力。

## 最终检查

- 决策单位是界面任务，而不是业务对象或现成组件。
- 字段宽度与业务含义、字段组和实际父容器一致。
- Table 与 DataTable 的选择来自用户任务；每项 DataTable 能力都有独立依据。
- 排序没有被误写为持久化重排，重排范围没有歧义。
- 增长型数据没有被客户端全量加载或仅靠虚拟化掩盖。
- 输出明确区分已确认事实、推荐决策和仍待用户确认的问题。
- 提问和方案没有扩展到当前交付物不需要解决的相邻业务规则。
- 数据契约前提没有被误当成修改其他系统的授权，也没有发明精确标识符。
