# 表格与数据规模

## 先判断是否需要表格

只有用户需要跨多条同类记录进行扫描、比较、排序、筛选或批量操作时，才选择表格。以图片识别、摘要阅读、层级浏览或异构内容为主时，选择符合信息结构的列表、卡片或树，不因“有多条数据”而使用表格。

## Table 与 DataTable

选择 **Table**，当任务以阅读和比较为主，数据集合具有可信边界，只需要基础展示和必要的行级访问。

选择 **DataTable**，当用户把记录集合当作数据工作区，并确实需要下列一种或多种能力：

- 排序或筛选。
- 分页或连续加载。
- 行选择和批量操作。
- 列显隐、调整或固定。
- 持久化重排。

每项能力独立确认。选择 DataTable 不代表启用完整功能包；需求和现有行为没有明确答案时，直接询问用户并给出推荐答案。

## 建立数据规模基线

分别确认：

1. **数据集总量**：决定查询、索引和服务端处理约束。
2. **单次返回量**：决定网络载荷和客户端内存。
3. **同时渲染量**：决定 DOM、滚动和交互性能。

同时确认当前数量级、可信上限或增长趋势，以及服务端是否支持排序、筛选和分页。无法从需求、契约或代码确认时，该缺口会改变架构，必须先询问用户。

`10¹`、`10²`、`10³`、`10⁴+` 等数量级用于暴露风险，不构成跨项目通用阈值。单元格复杂度、载荷、设备环境和用户操作方式共同决定实际方案。

## 决定处理位置

没有可信小规模上限或预计持续增长的数据集合，由服务端承担排序、筛选和分页。客户端全量加载后再处理只适用于已确认较小且稳定有界的数据集合。

虚拟化只减少同时渲染量，不减少数据集总量、查询成本、传输量或客户端持有量。它不能替代服务端集合操作；仅在同时渲染量和行渲染成本需要时单独评估。

## 区分排序与重排

- **排序**根据字段计算显示顺序，不修改业务数据。
- **重排**修改记录在业务中的明确顺序，并持久化结果。拖拽只是重排的一种交互方式。

仅当业务存在可编辑顺序时提供重排。开始设计前确认完整重排范围、持久化契约、用户权限以及结果影响。

分页、筛选、部分加载或按其他字段排序后的可见行，不自动构成重排范围。如果“拖到第三位”无法唯一解释为某个完整集合中的第三位，暂停实现并询问用户，不能把当前页位置写回为业务顺序。
